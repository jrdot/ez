# 목적

지정된 하나의 워크플로우를 검증하고 `-VERIFY.md` 보고서를 작성하라. 코드와 기준 문서는 수정하지 말라.

# 입력

1. 작업 브랜치/워크트리, 리비전, 워크플로우 ID와 범위를 확인하라. 브랜치명만으로 범위를 단정하지 말라.
2. 해당 워크플로우 개발 가이드를 필수 기준으로 읽어라. 없으면 검사를 중지하고 누락을 보고하라.
3. 존재하는 관련 문서 `docs/workflow/common.md`, 분야별 `common.md`, `docs/core/DESIGN_SPEC.md`, `docs/core/USER_REQUIREMENTS_SPEC.md`에서 현재 범위의 조항을 확인하라. 상위 문서에서 배정한 내용이 가이드에 누락되었는지 확인하라. 문서 간 충돌은 임의 해석하지 말고 기록하라.
4. 해당 `-HANDOFF.md`를 읽어 구현 주장, 변경 파일, 사용자 결정, 보류·범위 제외, 미구현, 테스트 기록과 후속 계약을 추출하라. HANDOFF가 없으면 누락을 적고 나머지 검사는 진행하라. HANDOFF만으로 PASS하지 말라.
5. 실제 소스, 테스트, 설정, 실행 결과, UI 및 Git 변경 내역을 검사하라. 적용되는 `AGENTS.md`의 작업 규칙을 따르라. 생성물과 의존성 디렉터리는 직접 관련될 때만 검사하라.

# 검사 절차

1. 가이드의 기능, 동작, UI, 데이터, 인터페이스, 제한, 예외 처리와 완료 조건을 독립적으로 판정할 수 있는 항목으로 분해하라. 확정 요구·조건부 요구·제안·후속 범위를 구별하라. 기존 요구 ID를 우선 쓰고 없다면 `VAL-FE03-001`처럼 안정적인 ID를 만들라.
2. [보고서 템플릿](assets/verify-template.md)에 먼저 `ID | 항목 | 요구 내용 | 기준 | 검사 대상` 체크리스트를 채워라. 요구 내용의 출처 위치를 기록하라.
3. HANDOFF의 구현·보류 주장을 실제 코드와 대조하라. 주장한 파일 또는 기능이 없거나 가이드와 다른 경우를 적으라. 요구하지 않은 추가 구현은 별도 발견 사항으로 기록하라.
4. 관련 코드와 테스트 동작을 확인하고 실행 가능한 범위의 검사를 실행하라. 명령, 검사 리비전, 결과와 미실행 사유를 남겨라. 과거 HANDOFF의 통과 기록은 현재 코드의 통과 증거가 아니다.
5. 항목마다 실제 결과, 파일 경로·가능하면 줄 번호, 테스트 근거와 판정 이유를 기록하라. 사용자 결정으로 보류했다면 결정의 출처와 현재 적용 범위를 확인하라. 원래 완료 조건이 남아 있으면 완료 처리하지 말라.
6. 요구사항 → 설계 → 가이드 → 구현 → 테스트 연결을 확인하고 끊긴 관계를 별도로 적으라. 현재 워크플로우 밖의 후속 기능은 범위 밖임을 밝히라.
7. 전체 건수, FAIL/WARNING/N/A 항목, 후속 조치와 미실행 범위를 요약하라. 원 가이드를 바꾸지 말고 같은 폴더에 `<가이드 파일명>-VERIFY.md`를 작성하라. 예: `03-OBJECTS-IMAGES-VERIFY.md`. 쓰기가 불가능하면 사용 가능한 곳에 작성하고 의도한 위치를 밝혀라.

# 판정 기준

- **PASS**: 해당 요구를 충족하는 실제 구현과 구체적인 확인 근거가 있다. 테스트가 필수 완료 조건이면 실행 결과도 확인하라.
- **FAIL**: 범위 안의 필수 구현이 없거나 기준과 명확히 다르거나 필수 테스트가 실패했다. HANDOFF의 보류 주장만으로 제외하지 말라.
- **WARNING**: 핵심 구현은 있으나 일부 차이, 잠재 결함, 증거·검증 부족이 있거나 승인된 보류로 원래 완료 조건이 남았다. 위험을 구체적으로 적으라.
- **N/A**: 조건이 발생하지 않았거나 명시적으로 현재 워크플로우의 범위 밖이다. 적용하지 않는 근거를 적으라. 자료 부족이면 결과에 '판정 보류(증거 부족)'를 쓰고 WARNING으로 분류하라.

완료와 미완료가 섞인 항목은 나누어 판정하라. 전체 완료는 범위 안의 필수 항목에 FAIL 및 미충족 완료 조건이 없을 때만 선언하라. 전체 판단의 자료가 부족하면 '판정 보류'로 기록하라.

# 보고 규칙

- 빈 셀은 `-`로 채우되 필수 판정 이유와 근거를 `-`로 대체하지 말라.
- 테스트 파일의 존재나 HANDOFF 주장만으로 PASS하지 말라.
- 문서에 없는 요구를 만들어내지 말고 문서 충돌·근거 없는 보류를 별도 기록하라.
- 코드를 고치지 말고 발견한 오류와 재현 방법을 보고하라.
- [보고서 템플릿](assets/verify-template.md)을 사용하라.
