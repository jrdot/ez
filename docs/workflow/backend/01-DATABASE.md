# BE-01 — PostgreSQL 영속화와 무결성

> 필수 선행: [전역 공통 원칙](../common.md), [Backend 공통](common.md). 계층 문서를 직접 열었더라도 먼저 읽는다.

책임: 서버 데이터의 물리 스키마, 제약·인덱스, 트랜잭션, 마이그레이션. 서버 실행·설정은 [백엔드 실행 안내](../../../backend/README.md)를 따른다. 로컬 IndexedDB, 도메인 의미, 서비스 호출, 백업 실행의 독립 설계 문서는 작성 예정이며 [문서 안내](../../README.md)에서 관리한다.

## 저장 대상 초안

아래는 제품 전체의 저장 책임 목록이다. 초기 구현은 `projects`와 `project_members`이며, 구체적인 결정과 보류 범위는 아래의 초기 구현 결정을 따른다.

| 테이블 | 저장 책임 | 설계 시 확인할 관계 |
|---|---|---|
| `projects` | 프로젝트 소유자·메타데이터·문서 버전·revision·공통 설정 | 사용자, 시트, 자산 |
| `project_members` | 프로젝트별 사용자 접근 권한 | 프로젝트·사용자별 중복 방지 |
| `sheets` | 시트 이름·순서와 부품·배선·주석 데이터 | 프로젝트 소속 |
| `parts` | 라이브러리/개인 부품 정의, 단자·규격·첨부 참조 | 소유자, 인스턴스의 `partId` |
| `assets` | 파일명·MIME·크기·해시·업로드 사용자·생성일·저장소 참조 | 프로젝트·부품 참조와 파일 객체 |

인증 사용자 테이블 또는 외부 인증 ID 매핑은 인증 방식 결정 후 추가한다. BOM 설정·수동 품목·가격의 저장 위치도 문서 스키마에 맞춰 결정한다. 자동 집계 결과는 원문에서 별도 테이블로 요구하지 않았다.

## 무결성과 접근

- 큰 이미지/PDF 바이너리는 DB 본문이 아닌 파일 저장소에 둔다.
- 프로젝트와 멤버·시트·자산의 관계, 삭제 시 처리 규칙, 사용자 범위의 조회 조건을 정의한다.
- JSON 본문 안의 부품·단자 참조는 애플리케이션 검증과 함께 관리한다.
- 문서 변경과 revision 갱신을 같은 트랜잭션에서 처리하고 기대 revision이 다르면 저장을 거부한다.
- 기본 구성은 애플리케이션용 DB 계정과 운영/마이그레이션 계정을 분리한다. 이번 배포는 사용자의 명시적 선택으로 `ezwire` 계정을 공통 사용한다. 상세 설정은 아래 결정을 따른다.
- 사용자·프로젝트 권한은 서버에서 반드시 검사한다. 원문의 RLS 제안은 추가 방어 수단으로 검토하되 채택 여부·정책은 미정이다.
- 미참조 자산만 정리할 수 있게 참조 관계와 삭제 정책을 설계한다.

## 구현 전 결정

1. `projects` 전체 JSONB와 `sheets` 분리 저장 중 본문 기준을 정한다. 양쪽에 본문을 중복 저장하는 구조를 기본으로 가정하지 않는다.
2. 부품·배선·주석을 JSONB로 저장할지 정규화할지 결정한다.
3. PK/FK, 삭제 정책, 역할 값, 필요한 unique 제약·조회 인덱스를 확정한다.
4. 파일 `version`, 문서 `formatVersion`, 서버 `revision`의 저장·변환 규칙을 정한다.
5. ORM/쿼리 계층·마이그레이션 도구와 RLS 사용 여부를 백엔드 담당과 결정한다.

## 구현 순서와 검증

저장 단위 합의 → 초기 스키마·마이그레이션 → 저장소 쿼리 → 권한·동시성 검증 순서로 진행한다.

프로젝트 저장/복원, 멤버 중복·잘못된 참조 방지, 실패 시 롤백, 동시 revision 갱신 중 하나만 성공하는지 검증한다. 스키마 변경 시 기존 문서와 자산 참조 보존을 확인하며 백업 복원은 인프라 담당과 검증한다.

## 초기 구현 결정 — 2026-09-22

이 절은 위 구현 전 결정 중 이번 DB 기반 작업에 필요한 항목을 확정한다. 인증·HTTP 계약·클라우드 기능 전체의 완료를 의미하지 않는다.

- 저장 본문은 `projects.document JSONB`의 **전체 `.wireproj` 객체** 하나다. `project.sheets`에 부품·배선·주석을, `project.bom`에 BOM 설정·수동 품목을 보존한다. 별도 `sheets` 테이블을 만들거나 본문을 중복 저장하지 않는다. `parts`, `assets`와 알 수 없는 확장 필드도 JSON 값 그대로 보존한다. JSONB 특성상 원본 공백·키 순서는 보존 대상이 아니다.
- `projects.id`는 기존 도메인과 샘플 파일을 수용하는 불투명 문자열 PK다. 파일의 `project.id`와 반드시 일치한다. 같은 ID의 생성은 덮어쓰지 않고 unique 위반으로 실패한다. 프로젝트 사본 생성 시 새 ID를 부여하는 정책은 서비스 계층에서 담당한다.
- `owner_id`는 신뢰된 서버 호출자가 제공한 인증 주체 문자열이다. 파일의 `project.ownerId`는 보존하지만 접근 권한에 사용하지 않는다. 인증 방식이 미정이므로 사용자 테이블/FK·계정 생성·소유권 이전은 추가하지 않는다.
- 파일 `version=1`과 `project.formatVersion=1`을 독립적으로 검사한다. 지원하지 않는 버전은 거부하며, 실제 이전 버전 계약이 생길 때 마이그레이션을 추가한다. 앱 버전은 문서 버전으로 사용하지 않는다.
- `projects.revision`은 서버 저장 토큰이다. 생성 시 0, 본문 저장 성공 시 1 증가하며 파일 내부 `project.revision`과 독립적이다. 파일 revision을 서버의 기대 revision으로 자동 변환하지 않는다. 호출자는 조회 결과의 서버 revision을 `expected_revision`으로 전달한다.
- `created_at`·`updated_at`은 서버의 timezone-aware 시각이다. 파일 내부 시각은 그대로 보존한다. 프로젝트 소유자·갱신 시각·ID와 멤버 사용자·프로젝트에 조회 인덱스를 둔다.
- `project_members`는 `(project_id, user_id)` 복합 PK와 `projects.id` FK를 사용한다. 역할은 `viewer`·`editor`이며 소유자는 `projects.owner_id`에서 관리한다. 프로젝트 삭제는 멤버 행에만 CASCADE한다. 파일 저장소의 객체를 삭제하지 않는다.
- 소유자는 본문 편집·멤버 관리·삭제, editor는 조회·본문 편집, viewer는 조회만 가능하다. 모든 조회는 사용자 범위로 제한하고, 미존재·접근 불가 프로젝트는 같은 오류를 반환한다. 파일 내용으로 권한을 부여하지 않는다.
- 저장·멤버 변경·삭제는 같은 프로젝트 행을 잠근다. 잠금 획득 후 권한과 기대 revision을 확인하며 본문·revision을 한 트랜잭션으로 갱신한다. 호출자가 `Session.begin()`으로 전체 작업의 commit/rollback을 소유한다. 기본 격리 수준은 PostgreSQL READ COMMITTED다.
- ORM은 SQLAlchemy 2, 드라이버는 psycopg 3, 스키마 이력은 Alembic이다. 앱 시작 시 자동 DDL을 실행하지 않는다. `backend/.env`를 소스 위치 기준으로 자동으로 읽고, 같은 이름의 환경변수를 우선한다. 사용자 요청에 따라 초기 배포는 DB·계정 이름을 모두 `ezwire`로 사용하며, `DB_HOST/DB_PORT/DB_NAME/DB_USER/DB_PASSWORD` 공통 설정으로 앱·마이그레이션을 연결한다. 이 구성에서는 앱도 DB 소유자의 DDL 권한을 가진다. 분리 계정 구성용 `DATABASE_URL`·`MIGRATION_DATABASE_URL`도 지원하며 해당 용도의 공통 설정보다 우선한다. 공통 설정이 없는 URL 전용 구성에서는 마이그레이션 URL을 런타임 URL로 대체하지 않는다. 실제 비밀번호가 담긴 `.env`는 Git에 포함하지 않는다. 운영 절차는 [백엔드 실행 안내](../../../backend/README.md)에 둔다.
- RLS는 이번 단계에 도입하지 않는다. 내부 저장소의 사용자 범위 조회·권한 검사가 현재 방어선이며, 인증 연동 후 HTTP 경로를 공개한다. 서버 호출자가 전달하는 actor ID가 검증되었다는 전제가 필요하다.

### 검증 경계와 후속 작업

DB와 저장소는 파일 envelope·버전·프로젝트 ID·시트 배열·parts/assets 배열을 검사한다. 부품·단자·배선의 의미적 참조와 전체 도메인 유효성은 서비스 계층이 검증해야 하며, 현재 저장소를 외부 입력 검증기로 사용하지 않는다.

독립 라이브러리 `parts` 테이블, 파일 메타데이터 `assets` 테이블, 자산 참조 FK·미참조 판별·물리 파일 삭제는 부품·첨부 계약 확정 후 구현한다. 이번 단계는 파일에 담긴 참조를 손실 없이 보존하며 바이너리 저장·업로드·정리를 제공하지 않는다. BOM 자동 집계 테이블도 만들지 않는다.

실제 PostgreSQL 통합 테스트는 Alembic 적용부터 저장/복원, 권한, 복합 PK/FK/역할 제약, 실패 롤백, 두 동시 저장 중 하나만 성공, 스키마와 모델 일치 및 재적용을 검증한다. 테스트는 무작위로 생성한 전용 스키마만 정리한다. 백업 복원과 향후 기존 버전 업그레이드 검증은 해당 운영·마이그레이션이 추가될 때 수행한다.

사용자 지정 서버 `192.168.0.4`의 PostgreSQL 18.6, DB·계정 `ezwire`에 초기 마이그레이션 `0001`을 적용했다. 적용 전 기본 스키마에 테이블이 없음을 확인했고 적용 후 `alembic current`·`alembic check`로 버전과 모델 일치를 확인했다. 전체 통합 테스트는 별도 PostgreSQL 17 테스트 DB에서 수행했으며 사용자 DB에 테스트 데이터를 넣지 않았다. DB 기반 코드는 main에 포함되어 있다. web 서버의 코드 배포·환경설정 반영 여부는 배포 시 별도로 확인한다.
