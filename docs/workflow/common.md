# 공통 — 제품 목적·목표·개발 원칙

**모든 워크플로우 에이전트의 필수 컨텍스트다.** 이 문서를 먼저 읽고 담당 계층 설계를 읽는다. 기능·동작의 기준은 [사용자 요구사항 규격서](../core/USER_REQUIREMENTS_SPEC.md)와 [설계 규격서](../core/DESIGN_SPEC.md)다. 이 문서는 전역 업무 원칙과 기존 제품 계획을 다루며, 영역별 공통 문서와 작업 문서는 이를 구현하는 방법과 검증을 다룬다. 기존 계획을 core의 확정 범위에 자동 편입하지 않는다.

## 목적과 사용자

`ezwire`는 전자 부품을 캔버스에 배치하고 실제 연결 관계를 배선으로 표현하며, 프로젝트 문서와 BOM을 함께 관리하는 웹 기반 설계 도구다.

주요 사용자는 마이크로컨트롤러·센서·모듈 개발자, 소규모 전자제품·하네스·프로토타입 제작 엔지니어, 제작 문서와 부품 목록을 관리하는 팀, 연결 관계를 설명하는 교육 사용자다.

핵심 목표는 부품과 단자를 연결하고, 작업을 잃지 않고 저장·복구하며, 다른 사람이 읽고 제작할 수 있는 BOM과 출력물을 만드는 것이다. 회원가입 없이 새 프로젝트를 시작해 10분 안에 간단한 배선도를 완성할 수 있어야 한다.

## 공통 사용자 흐름과 용어

`프로젝트 생성/열기 → 부품 선택·배치 → 단자 연결 → 시트·라벨·주석·BOM 정리 → 저장·복구 → 출력·공유`

- 프로젝트는 문서 단위, 시트는 배선도 한 장이다. BOM·팔레트·설정은 프로젝트 공통이고 부품·배선·주석은 시트별이다.
- 라이브러리 부품 정의와 캔버스 인스턴스는 구분한다. 사용자 변경으로 원본 라이브러리를 훼손하지 않는다.
- BOM은 여러 시트의 동일 부품을 합산하는 제작용 부품 목록이며, 가격 미입력도 정상 상태다.
- 자동저장, 프로젝트 파일 내보내기, 서버 동기화는 서로 다른 저장 상태다.

## 초기 제품 범위와 성공 기준

Phase 1의 편집기 MVP는 중간 단계다. 초기 제품 전체의 완료는 다음 사용자 기능을 포함한다.

1. 부품 추가·이동·회전·삭제.
2. 단자 간 배선 생성과 색상·굵기·경로 수정.
3. 텍스트 주석과 부품 라벨 작성.
4. 프로젝트 파일 저장과 다시 열기.
5. 브라우저 새로고침·재실행 후 마지막 작업 복구.
6. 여러 시트의 부품을 하나의 BOM으로 집계하고 수동 품목 추가.
7. 부품 이미지·데이터시트와 프로젝트 참고 이미지 첨부.
8. 배선도 PNG/SVG/PDF, BOM CSV/PDF 출력과 첨부 참조 유지.

계정·클라우드·개인/팀 권한·공유 링크·기기 간 충돌 복구는 Phase 5, 요금제·사용량·결제는 Phase 6이다. 로컬 편집기 개발이 서버 구현을 기다리지 않도록 한다.

초기 제외: PCB 패턴 설계, 회로 시뮬레이션, 자동 배선, 전기 규칙 검사, 실시간 협업. 정렬·간격 맞춤은 2차 기능이다. 그룹화는 현재 요구사항·설계 규격과 FE-01/03을 따른다. 정밀 편집은 데스크톱을 우선하고 모바일은 조회·간단한 수정부터 지원한다.

## 모든 계층이 지켜야 할 원칙

- **로컬 우선·데이터 보존:** 네트워크가 끊겨도 편집을 계속하고, 저장 실패 원인을 표시하며, 파일·복구 과정에서 문서와 첨부 참조를 보존한다.
- **버전과 충돌:** 프로젝트 데이터는 UTF-8과 명시적 버전으로 관리한다. 이전 포맷은 마이그레이션하고 여러 탭/기기의 저장 충돌을 감지한다. 파일 포맷 버전·앱 버전·문서 revision을 구분한다.
- **권한과 격리:** 사용자 프로젝트·첨부파일을 권한 없는 사용자에게 노출하지 않는다. 접근 권한과 후속 요금제 한도는 서버에서 검증한다.
- **성능:** 일반 프로젝트의 초기 편집 화면 표시 목표는 2초 이내다. 부품 100개·배선 300개에서 기본 이동·선택이 끊기지 않아야 한다.
- **책임 분리:** 도메인 규칙, 화면·입력, 저장 어댑터, HTTP 계약, 서버 서비스, 물리 DB를 구분한다. 계층 간 계약 변경은 영향받는 문서와 검증에 함께 반영한다.
- **구현 기반:** Next.js/TypeScript 웹앱, SVG 렌더러, IndexedDB 로컬 저장, 현재 FastAPI 백엔드, PostgreSQL·파일 저장소를 출발점으로 한다. 자체 호스팅 가능성을 유지하고 Supabase를 필수 의존성으로 두지 않는다.
- **참고 코드:** 기존 EasyCable은 기능·흐름 참고용이며 구현 코드를 그대로 복사하지 않는다.

## 단계와 인계 기준


| 단계          | 주 작업과 담당                                     | 완료 기준                         |
| ----------- | -------------------------------------------- | ----------------------------- |
| 0 기반        | 프런트엔드 초기화, 도메인·파일 포맷 초안, CI·관리 도구            | 빈 프로젝트 열기/닫기, 타입 검사·테스트 실행    |
| 1 편집기 MVP   | 프런트엔드·도메인: SVG, 부품·단자·배선, 스냅, Undo/Redo      | 부품 10개 이하의 배선도를 만들고 같은 상태로 재현 |
| 2 문서화·저장    | 프런트엔드·로컬 저장: 시트, 라벨·주석, 속성, 파일 I/O, 자동복구     | 새로고침·브라우저 재실행 후 마지막 작업 복구     |
| 3 라이브러리·BOM | 도메인·프런트엔드: 사용자 부품, 검색·필터, 자동/수동 BOM, CSV/PDF | 여러 시트의 동일 부품이 한 행에 정확히 합산     |
| 4 첨부·출력     | 프런트엔드·로컬 저장: 이미지/PDF, 미리보기·삭제, PNG/SVG/PDF   | 저장·열기·출력 후 첨부 참조 유지           |
| 5 계정·클라우드   | API·백엔드·DB·프런트엔드: 로그인, 개인/팀 권한, 공유, 충돌       | 두 사용자의 읽기·편집 권한이 서버에서 적용      |
| 6 상용화       | 백엔드·인프라: 요금제, 사용량, 결제, 오류 추적, 보존·삭제 정책       | 상세 출시 기준은 해당 단계에서 확정          |


첫 구현 순서: 앱 초기화 → 도메인 타입·샘플 JSON → SVG 좌표계 → 부품 배치·드래그 → 단자 연결 → 저장/열기·Undo/Redo → 핵심 흐름 Playwright 고정. 계정·서버 저장 완성을 기다리지 않고 로컬 편집기를 개발한다.

## 공통 작업 기준

설계 기록은 저장소 Markdown, 코드·PR·CI는 GitHub(`jrdot/ezwire`), 작업 상태의 기준은 Linear다. GitHub Projects는 보조 뷰이며 작업을 독립적으로 중복 관리하지 않는다.

설계의 미정 항목을 확정된 계약처럼 구현하지 않는다. 해당 기능 착수 시 담당 문서에서 결정을 기록하고, 요구사항·관련 검증·문서 변경을 함께 완료한다. CI의 현재 실행 항목은 `.github/workflows/ci.yml`을 따른다. 브랜치·PR·릴리스 운영 세부를 담을 인프라 문서는 작성 예정이며 [문서 안내](../README.md)에서 관리한다.
