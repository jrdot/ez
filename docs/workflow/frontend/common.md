# Frontend 공통 — 업무 범위·워크플로우·인계 기준

대상은 이 저장소에서 frontend를 구현·검증·인계하는 워크플로우 에이전트다. 이 문서는 구현 작업 지침이며, 기능 구현 완료 보고서가 아니다.

기준: [사용자 요구사항 Draft v0.1](../../core/USER_REQUIREMENTS_SPEC.md), [설계 Draft v0.1](../../core/DESIGN_SPEC.md). 저장소 구현 확인일: 2026-09-23. 두 원문은 바깥쪽 Markdown 코드 펜스가 포함되어 있으므로 렌더링 결과가 아닌 원문 제목과 ID로 참조한다.

## 읽는 순서와 규격 적용

1. [기존 공통 원칙](../common.md)으로 제품 배경·계층 책임을 파악한다.
2. 두 규격서를 읽고 이 가이드와 [요구사항 추적표](07-TRACEABILITY.md)를 읽는다.
3. 수행할 단계 문서와 선행 단계의 인계 결과를 읽는다.
4. 실제 코드·테스트·작업 트리 변경을 다시 확인한다. 아래 현황을 영구적인 사실로 간주하지 않는다.

이번 frontend 작업의 기능·동작 기준은 새 두 규격서다. 요구사항은 사용자 동작을, 설계는 이를 구체화한 표현과 개념을 정의한다. 서로 충돌하면 한쪽을 임의로 버리지 말고 해당 ID와 선택지를 기록한다. 규격에 없는 UI 수치·자료구조·알고리즘은 이 문서에서 **구현 제안**으로 다룬다. 일상적인 구현 선택은 에이전트가 근거와 함께 기록하고 진행하되, 출력물 의미·데이터 손실·사용자 동작을 바꾸는 미정 사항은 해당 부분 구현 전에 확인한다. 독립 작업은 계속한다.

[전역 공통 문서](../common.md)와 아래 기존 프런트엔드 개요의 Phase 번호와 아래 FE 번호는 별개다. 기존 문서의 그룹화 후순위, 모바일 일부 지원, SVG/CSV 출력·계정·공유·자동저장 등은 새 규격의 확정 범위로 자동 편입하지 않는다. 자동 경로 생성은 사용자가 지정한 배선의 90°/45° 경로를 만드는 기능이며, 회로 전체 자동 배선 기능과 구분한다.

## 실행 워크플로우

| 단계 | 문서 | 선행 조건 | 검토 가능한 결과 / 종료 게이트 |
|---|---|---|---|
| FE-01 | [계약·편집기 기반](01-FOUNDATION.md) | 두 규격과 현재 코드 확인 | 기본값·객체/배선 계약·명령 이력·호환성 방침 결정 |
| FE-02 | [레이아웃·페이지·탐색](02-WORKSPACE.md) | FE-01의 좌표·페이지·상태 계약 | 5영역 화면, 3페이지 제한, 줌/팬/스냅 조작 검증 |
| FE-03 | [객체·부품·이미지 편집](03-OBJECTS-IMAGES.md) | FE-01 명령, FE-02 좌표 변환 | 라이브러리에서 등록·배치·편집, 단자와 이력 검증 |
| FE-04 | [배선·분기·교차](04-WIRING.md) | FE-03의 실제 단자와 변환 | 세 배선 타입, 미리보기, 분기, Jump, 경로 편집 검증 |
| FE-05 | [보조 기능·저장·출력 연계](05-INTEGRATIONS.md) | FE-03/04 문서 계약 | 확정된 보조 기능 구현, 미정 기능 계약·연동 상태 명시 |
| FE-06 | [통합 검증·인계](06-VALIDATION.md) | 각 기능 게이트와 필요한 결정 완료 | 요구사항별 증거, 회귀 검증, 잔여 제한을 포함한 인계 |

권장 순서는 `FE-01 → FE-02 → FE-03 → FE-04 → FE-05 → FE-06`이다. FE-05의 계약 조사·샘플 준비는 앞 단계 중에도 진행할 수 있다. FE-04는 ① 세 타입 생성·Preview ② 분기·교차 ③ 경로 편집 순서의 작은 작업으로 나눈다. 각 작업마다 검증하며 FE-06까지 테스트를 미루지 않는다. 이 워크플로우는 한 에이전트가 순차 실행할 수 있으며 별도 에이전트 생성이 필수는 아니다.

## 에이전트 공통 작업 규칙

- UI, 입력 상태, 도메인 계산, 파일/이미지/서비스 어댑터를 분리한다. React 컴포넌트에 배선 규칙을 직접 누적하지 않는다.
- 모드·선택·드래그 Preview는 편집 상태, 확정된 객체·배선은 문서 상태다. 화면 표시용 Jump는 연결 그래프를 바꾸지 않는다.
- 규격 ID → 구현 파일 → 검증 증거를 연결한다. 버튼 배치나 타입 선언만으로 기능 완료 처리하지 않는다.
- 미정 기능은 동작하지 않는 성공 버튼으로 만들지 않는다. 기능의 상태를 명확히 표시하고 완료 목록에서 제외한다.
- 기존 사용자 변경을 보존한다. 구현 시작 시 `git status --short`를 확인하고 무관한 코드·문서를 되돌리지 않는다.
- 계정·API·DB 구현은 frontend 작업에 임의로 포함하지 않는다. 필요한 입출력·오류·취소 계약과 샘플을 작성해 담당 계층에 인계한다.

## 매 작업의 입력과 인계 형식

작업 입력은 `단계/세부 작업`, `대상 REQ/DES ID`, `선행 결과`, `이번 범위`, `결정이 필요한 사항`이다. 아래 형식으로 결과를 남기면 다음 실행이 이어받을 수 있다.

```text
단계 / 상태: FE-xx / 진행 중 | 검증 완료 | 일부 대기
대상 요구사항: REQ-..., DES-...
변경 파일과 사용자 동작:
계약 결정: 확정 요구 / 구현 선택 / 확인 필요를 구분
검증: 명령·시나리오·결과·증거 위치 (미실행은 이유)
남은 문제와 영향받는 요구사항:
다음 작업 및 시작 조건:
```

문서·샘플만 준비한 상태, mock 연동 완료, 실제 서비스 연동 완료를 구분한다. 미정 항목 때문에 일부 기능이 대기하는 경우 해당 항목을 숨긴 채 전체 규격 준수를 선언하지 않는다.

## 기존 프런트엔드 개요 — 제품 계획 참고

아래 Phase는 기존 제품 계획이며 FE-01~06 단계와 다르다. 그룹화·모바일·저장·출력 등 범위 차이는 위 규격 적용 원칙을 따른다. 현재 작업의 확정 범위는 core 규격과 단계별 작업 문서에서 확인한다.

책임: 화면, SVG 렌더링, 입력과 명령 이력, 라이브러리/BOM UI, 출력. 계산 규칙·로컬 저장·API의 독립 설계 문서는 작성 예정이며, 현재 문서는 [문서 안내](../../README.md)에서 확인한다.

### 스택과 배치

현재 Next.js + TypeScript, React, Tailwind CSS와 SVG 커스텀 렌더러를 사용한다. shadcn/ui, Zustand, Immer는 기존 설계의 도입 후보이며 아직 설치하지 않았다.

프런트엔드는 저장소 루트에서 실행하며 실제 소스는 `src/`에 둔다.

```text
src/
  app/                 라우트·페이지·레이아웃·전역 스타일
  components/          공통 UI·아이콘
  features/
    editor/            편집기 셸·SVG 캔버스
    project/           프로젝트 생성·열기 화면
  domain/              타입·파일 포맷·편집 규칙·단위 테스트
e2e/                   Playwright 시나리오 (저장소 루트)
```

향후 라이브러리·BOM은 `src/features/library/`, `src/features/bom/`, 저장 어댑터는 `src/persistence/`, 출력은 `src/export/`에 둔다. 별도 렌더러 계층이 필요해지면 `src/renderer/`로 분리한다. 해당 기능 구현 시 폴더를 생성한다.

### 상태와 변경 흐름

| 상태 | 내용 |
|---|---|
| `documentState` | 프로젝트·시트·부품·배선·BOM |
| `editorState` | 선택·활성 도구·활성 시트·줌·드래그 |
| `uiState` | 패널·모달·알림 |
| `sessionState` | 로그인·저장·동기화 상태 |

`execute(command) → documentState 변경 → history 기록 → 자동저장 예약 → 렌더링 갱신`을 기본 흐름으로 둔다. 드래그 등의 한 동작을 한 번에 Undo/Redo할 수 있어야 한다. 전체 JSON 스냅샷 이력이 커지지 않도록 명령 또는 패치 단위로 관리한다.

### 기능별 구현 순서

| 단계 | 구현 내용 |
|---|---|
| 0~1 | 빈 레이아웃·SVG 좌표계, 부품 추가/선택/이동/삭제, 단자 렌더링·연결, 확대/축소/패닝, 그리드·스냅, Undo/Redo |
| 2 | 다중/박스 선택, 복제·회전·크기 조절, 여러 시트, 라벨·주석, 배선 중간점 추가/이동·색상/굵기/스타일, 속성 패널, 저장/복구 UI |
| 3 | 라이브러리·개인 부품 등록·검색/필터, BOM 자동 집계 결과·수동 행·선택적 가격 편집, CSV/PDF BOM 출력 |
| 4 | 부품/프로젝트 이미지·데이터시트 PDF, 미리보기·삭제, PNG/SVG/PDF 배선도 출력, 인쇄 레이아웃 |
| 5 | 로그인·개인/팀 프로젝트·공유 UI, 서버 저장·충돌 표시 |

정렬·간격 맞춤은 2차 기능이다. 그룹화는 현재 요구사항·설계 규격과 FE-01/03을 따른다. 모바일은 조회·간단한 수정부터 지원하고 정밀 편집은 데스크톱을 우선한다.

### 저장·출력 연동

- 문서 변경 후 저장 담당 어댑터를 호출하고 `저장 중 / 저장됨 / 저장 실패`를 표시한다. 실패 원인을 사용자가 이해할 수 있게 설명한다.
- 로컬 자동저장·파일 저장·서버 동기화 상태를 혼동하지 않게 표시한다.
- BOM UI는 도메인 집계 결과를 사용하며 활성 시트만 집계하지 않는다.
- 큰 이미지는 원본과 화면용 해상도를 분리한다. 출력 전용 SVG/HTML 레이아웃으로 도면과 BOM이 잘리지 않게 한다.
- 서버 권한을 UI 기능 플래그만으로 대신하지 않는다.

### 완료·검증 기준

- Vitest: 좌표 변환·회전·스냅은 도메인 테스트를 사용하고 명령 이력의 Undo/Redo를 검증한다.
- Playwright: 부품 추가 → 연결 → 저장 → 재실행, 시트 2개 저장/열기, 한 동작 단위 Undo/Redo, 자동복구·여러 탭 충돌 표시를 검증한다.
- 첨부 이미지/PDF 복구, 빈 시트/내용 있는 시트의 저장 상태, PDF 도면/BOM 잘림을 확인한다.
- 일반 프로젝트 초기 편집 화면 표시 목표는 2초 이내다. 부품 100개·배선 300개에서 기본 이동·선택이 끊기지 않아야 한다. 측정 환경은 성능 검증 시 기록한다.
