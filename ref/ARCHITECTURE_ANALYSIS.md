# EasyCable 사이트 구조 및 확장 설계 기록

> 작성 목적: 백업해 둔 EasyCable 사이트를 참고하여, 유사 기능을 가진 독자적인 웹앱을 설계할 때 활용한다.
>
> 분석 범위: `index.html`, `styles.css`, `js/`의 정적 소스와 보조 파일. 실행 환경을 직접 검증한 결과가 아니라 소스 정적 분석 결과다.

## 1. 서비스 성격

EasyCable은 브라우저에서 전자 배선도를 그리는 편집기다. 사용자는 부품을 캔버스에 배치하고 단자를 배선으로 연결하며, 주석과 라벨을 추가한다. 프로젝트는 여러 장의 배선도(시트)를 포함할 수 있고, 부품 목록과 BOM을 함께 관리한다. 완성 결과는 프로젝트 파일로 저장하거나 PDF/이미지로 출력할 수 있다.

핵심 사용 흐름은 다음과 같다.

```text
새 프로젝트 또는 기존 프로젝트 열기
  → 부품 라이브러리에서 부품 선택
  → 캔버스 배치·회전·크기 조절
  → 단자 연결 및 배선 경로 편집
  → 라벨·주석·색상·BOM 정리
  → 자동저장/파일 저장
  → PDF 또는 PNG로 공유
```

## 2. 백업 폴더 구조

```text
easycable/
├─ index.html                         앱 화면, 모달, 패널, 스크립트 로딩
├─ privacy.html                       개인정보처리방침
├─ styles.css@v=16285378.css           화면 및 인쇄 스타일
├─ robots.txt                         크롤러 정책 파일(뒤쪽에 HTML이 섞여 있음)
├─ js/
│  ├─ app.js                          부트스트랩과 대부분의 UI 이벤트 연결
│  ├─ model.js                        프로젝트/시트/부품/배선 데이터 모델
│  ├─ render.js                       SVG 렌더링
│  ├─ interactions.js                 마우스·키보드 편집 동작
│  ├─ geometry.js                     좌표 변환, 스냅, 경로 계산
│  ├─ termeditor.js                    단자 편집
│  ├─ bgremove.js                     이미지 배경 제거
│  ├─ library.js                      부품 라이브러리
│  ├─ presets.js                      사용자 단자 프리셋
│  ├─ store.js                        IndexedDB 자동저장/복구
│  ├─ assets.js                       이미지·PDF 첨부물 저장 및 중복 제거
│  ├─ history.js                      Undo/Redo
│  ├─ io.js                           `.ezc`/JSON 파일 저장·열기
│  ├─ pdf.js                          인쇄용 PDF 화면 구성
│  ├─ i18n.js                         한국어/영어
│  ├─ awg.js                          전선 규격 관련 계산
│  ├─ flags.js                        기능 플래그
│  ├─ auth.js                         Supabase 인증
│  └─ pro.js                          무료/Pro 제한
└─ cdn-cgi/                           Cloudflare 이메일 복원 스크립트
```

`index.html`이 ES Module이 아닌 일반 `<script>` 태그로 모든 파일을 순서대로 로드한다. 따라서 전역 객체 `window.WE`가 사실상의 모듈 레지스트리이자 공유 상태다.

## 3. 주요 모듈과 책임

| 영역 | 주요 파일 | 확인된 책임 |
|---|---|---|
| 앱 조립 | `app.js` | 초기화, 툴바, 모달, 라이브러리, BOM, 설정, 피드백, 단축키 |
| 데이터 모델 | `model.js` | 프로젝트 메타데이터, 여러 시트, 부품·배선·주석, 팔레트, BOM 설정 |
| 화면 | `render.js` | SVG 요소로 부품, 단자, 배선, 라벨, 워터마크 렌더링 |
| 입력 | `interactions.js` | 선택, 이동, 드래그, 연결, 확대/축소, 키보드 조작 |
| 수학/기하 | `geometry.js` | 화면 좌표↔캔버스 좌표, 회전·스케일, 그리드 스냅, 배선 경로 |
| 저장 | `store.js` | IndexedDB 자동저장, 다른 탭 충돌 방지, 문서 복구 |
| 자산 | `assets.js` | 큰 data URL을 해시 키로 치환하고 자산 풀에 중복 없이 보관 |
| 파일 I/O | `io.js` | File System Access API 우선 사용, 미지원 브라우저는 다운로드 방식으로 대체 |
| 이력 | `history.js` | JSON 스냅샷 기반 Undo/Redo, 최대 80단계 |
| 출력 | `pdf.js` | 인쇄용 페이지·BOM·범례 구성 후 브라우저 인쇄 호출 |
| 계정/요금 | `auth.js`, `flags.js`, `pro.js` | Supabase 인증, preview 주소별 기능 플래그, 배선 수 제한 |

## 4. 데이터 모델

프로젝트는 여러 시트를 포함한다.

```text
project
├─ meta: { id, name, version, canvas }
├─ sheets[]
│  └─ { id, name, note, components[], wires[], annotations[] }
├─ palette[]
├─ manualBom[]
├─ bomPrice{}
├─ bomOrder[]
├─ bomColShow{}
├─ bomExtraCols[]
└─ bomCustom{}
```

런타임 편의를 위해 `project.components`, `project.wires`, `project.annotations`는 현재 활성 시트의 배열을 가리키는 getter/setter 별칭으로 구현되어 있다. JSON 저장 시에는 별칭이 저장되지 않고 `sheets`만 저장된다. 전체 프로젝트 집계(BOM, 배선 수, 자산 수집 등)는 반드시 `allComponents()`, `allWires()`, `allAnnotations()` 계열을 사용해야 한다.

이 설계는 기존 코드 수정량을 줄이는 장점이 있지만, 활성 시트와 전체 프로젝트의 구분을 놓치면 데이터 누락 버그가 생길 수 있다. 새 웹앱에서는 처음부터 `activeSheet`와 `project.sheets`를 명시적으로 분리하는 편이 안전하다.

## 5. 저장과 복구

- IndexedDB 데이터베이스 이름은 `wiringEditor`다.
- `state` 저장소에는 자동저장 문서와 스냅샷을, `assets` 저장소에는 이미지/PDF 자산을 보관한다.
- 자동저장과 파일 저장은 별개다. 파일에 마지막으로 저장한 JSON과 현재 상태를 비교하여 닫기 전 변경 여부를 판단한다.
- 첨부물은 내용 해시를 키로 사용하고, 프로젝트 안에는 `@ezc:<key>` 참조를 넣어 중복 저장을 줄인다.
- `.ezc` 파일은 프로젝트와 사용한 부품 정보·첨부물을 함께 묶는 이동용 포맷이다.
- Chrome/Edge에서는 File System Access API가 있으면 같은 파일에 다시 저장하고, 다른 브라우저에서는 파일 다운로드 방식으로 대체한다.

새 앱에서는 저장 포맷을 처음부터 명세화하는 것이 좋다.

```json
{
  "format": "my-wiring-app",
  "version": 1,
  "project": { "meta": {}, "sheets": [], "bom": {} },
  "assets": {}
}
```

버전 마이그레이션 함수를 두고, 모든 파일 읽기 시 최신 내부 모델로 변환하면 이후 기능 추가가 쉬워진다.

## 6. 참고할 만한 제품 기능

기능 우선순위를 다음처럼 나누면 개발 범위를 관리하기 쉽다.

### 1차: 편집기 핵심

- SVG 또는 Canvas 기반 작업 영역
- 부품 배치, 이동, 회전, 크기 조절
- 단자 선택과 배선 연결
- 그리드 스냅 및 확대/축소
- 선택 삭제, 복제, Undo/Redo
- 프로젝트 파일 저장/열기

### 2차: 생산성 기능

- 여러 시트
- 부품 라이브러리와 사용자 부품 등록
- 라벨/주석
- 배선 색상·굵기·경로 스타일
- 자동저장과 새로고침 복구
- BOM 자동 집계 및 수동 품목 추가

### 3차: 공유·상용화 기능

- PDF/PNG 출력
- 부품 데이터시트·이미지 첨부
- 사용자 계정과 클라우드 동기화
- 프로젝트 공유 링크와 권한
- 요금제와 사용량 제한
- 변경 이력 또는 협업 편집

## 7. 새 웹앱으로 업그레이드할 때의 권장 구조

기존 사이트는 단일 `app.js`와 전역 `WE`에 기능이 많이 모여 있다. 새 앱은 다음 경계를 두는 것이 좋다.

```text
src/
├─ domain/       프로젝트 모델, 배선 규칙, BOM 계산, 파일 포맷
├─ editor/       선택·드래그·연결·단축키·상태 전이
├─ renderer/     SVG/Canvas 렌더러와 히트 테스트
├─ persistence/  IndexedDB, 파일 I/O, 클라우드 저장
├─ catalog/      부품 라이브러리와 자산 처리
├─ export/       PDF·PNG·CSV 출력
├─ ui/            툴바, 속성 패널, 모달, 설정
└─ app/           라우팅, 인증, 기능 플래그, 부트스트랩
```

상태 관리도 다음처럼 분리하는 편이 좋다.

- `documentState`: 현재 프로젝트의 실제 데이터
- `editorState`: 선택 항목, 활성 도구, 줌, 드래그 중 여부
- `uiState`: 열려 있는 패널과 모달
- `sessionState`: 로그인, 저장 상태, 동기화 상태

렌더러는 상태를 읽어 화면을 그리기만 하고, 저장소나 DOM 이벤트를 직접 다루지 않게 하면 테스트와 교체가 쉬워진다.

## 8. 기존 백업에서 발견된 위험 요소

1. `app.js`가 약 234KB로 매우 크며 UI, BOM, 라이브러리, 설정, 피드백까지 담당한다. 기능이 늘면 회귀 위험이 커진다.
2. 전역 `WE`와 직접 DOM 조작에 강하게 결합되어 있어 개별 모듈 단위 테스트가 어렵다.
3. Undo/Redo가 프로젝트 전체 JSON 스냅샷을 700ms 간격으로 만든다. 이미지가 많거나 프로젝트가 커지면 메모리와 CPU 사용량이 증가할 수 있다.
4. `sample.ezc`와 `js/vendor/supabase.js`가 백업 폴더에 보이지 않는다. 샘플 불러오기 또는 인증 기능은 배포 환경에 따라 실패할 수 있다.
5. `robots.txt` 후반부에 HTML 문서가 섞여 있다. 배포 전 robots 파일과 HTML 파일을 분리해야 한다.
6. Supabase URL, GA4, Web3Forms 등 외부 서비스 의존성이 코드에 들어 있다. 새 앱에서는 환경 변수와 서비스 어댑터로 격리한다.
7. Pro 제한은 브라우저의 기능 플래그와 UI 검사를 중심으로 하므로 보안 경계가 아니다. 실제 과금·권한 판단은 서버에서 검증해야 한다.
8. 원본 HTML 일부가 인코딩이 깨진 상태로 보인다. 실제 배포본이 UTF-8인지 확인하고, 새 앱은 모든 소스와 데이터의 인코딩을 UTF-8로 고정한다.

## 9. 개발 로드맵 제안

### 단계 A: 제품 정의

타깃 사용자를 정하고, 반드시 필요한 부품 종류·배선 규칙·출력 양식을 먼저 정한다. “범용 회로도 편집기”보다 특정 작업(예: 마이크로컨트롤러 배선, 하네스 제작, 교육용 배선도)에 집중하면 초기 완성도가 높아진다.

### 단계 B: 로컬 MVP

부품 배치, 단자 연결, 이동/삭제, Undo/Redo, JSON 저장/열기, PNG 출력까지만 구현한다. 이 단계에서는 계정·결제·클라우드 동기화를 넣지 않는다.

### 단계 C: 작업 지속성

IndexedDB 자동저장, 문서 복구, 다중 시트, 부품 라이브러리, BOM을 추가한다. 저장 포맷 버전과 마이그레이션 테스트를 함께 만든다.

### 단계 D: 공유와 협업

PDF, 프로젝트 공유, 로그인, 클라우드 저장을 추가한다. 파일 저장과 서버 저장의 충돌 해결 규칙을 먼저 정의한다.

### 단계 E: 상용화

서버에서 권한과 사용량을 검증하고, 결제·요금제·감사 로그를 붙인다. 브라우저의 `LAUNCH` 플래그만으로 접근을 통제하지 않는다.

## 10. 반드시 검증할 시나리오

- 시트 1과 시트 2에 각각 부품을 넣은 뒤 저장하고 다시 열었을 때 모두 복원되는가
- 다른 이름의 두 탭에서 작업할 때 자동저장이 서로 덮어쓰지 않는가
- 이미지/PDF 첨부물이 포함된 프로젝트를 다른 브라우저에서 열 수 있는가
- 저장하지 않은 변경이 있을 때 닫기 경고가 나타나는가
- Undo/Redo가 한 번의 드래그를 여러 단계로 쪼개지 않는가
- 회전한 부품의 단자에 배선이 정확히 연결되는가
- BOM 수량·단가·합계가 여러 시트의 부품을 모두 집계하는가
- 빈 시트와 내용이 있는 시트를 오갈 때 저장·복구 판정이 정확한가
- PDF 출력에서 시트, 범례, BOM, 주석이 잘리지 않는가
- 기능 플래그가 꺼져 있을 때 로그인·요금제 코드가 기본 편집을 방해하지 않는가
