# 목적

`-HANDOFF.md` 하나로 지정된 워크플로우를 검증하고 `-VERIFY.md` 보고서를 작성하라. 사람의 응답 없이 끝까지 실행될 수 있어야 한다. 소스 코드와 기준 문서는 수정하지 말라. 이 스킬이 쓰는 파일은 `-VERIFY.md` 하나뿐이다.

# 입력

- **필수:** HANDOFF 파일 경로. 예: `docs/workflow/frontend/01-FOUNDATION-HANDOFF.md`
- **선택:** 작업 브랜치(예: `feature/01-FOUNDATION`), 비교 기준 리비전.

입력이 없으면 현재 브랜치에서 변경된 `docs/workflow/**/*-HANDOFF.md`를 찾아라. 정확히 하나가 아니면 검사하지 말고 후보 목록을 보고하라.

# 사전 확인 (하나라도 실패하면 중지)

1. **작업 트리:** `git status --porcelain`이 비어 있지 않으면 검사를 중지하라. 변경·미추적 파일 목록과 "커밋되지 않은 변경으로 검사 중지"를 보고하라. VERIFY 파일도 쓰지 말라.
2. **리비전:** 현재 브랜치, `HEAD` 커밋, 기준 브랜치(`main`)와의 merge-base를 기록하라. 브랜치명만으로 범위를 단정하지 말라.
3. **기준 가이드:** HANDOFF 파일명에서 `-HANDOFF`를 제거한 같은 폴더의 파일이 기준 가이드다(`01-FOUNDATION-HANDOFF.md` → `01-FOUNDATION.md`). 없으면 검사를 중지하고 누락을 보고하라.
4. **영역과 ID 접두사:** 폴더로 영역을 정하라. `frontend` → `FE`, `backend` → `BE`. 파일명 앞 번호와 합쳐 워크플로우 ID로 쓴다(예: `FE01`, `BE01`).

# 기준 문서

1. 기준 가이드(필수 기준).
2. 존재하는 상위 문서: `docs/workflow/common.md`, 해당 영역 `common.md`, `docs/core/DESIGN_SPEC.md`, `docs/core/USER_REQUIREMENTS_SPEC.md`. 현재 범위에 해당하는 조항만 확인하라. 상위 문서가 이 워크플로우에 배정한 내용이 가이드에 빠졌는지 확인하라. 문서 간 충돌은 임의로 해석하지 말고 기록하라.
3. HANDOFF: 구현 주장, 변경 파일, 사용자 결정, 보류·범위 제외, 미구현, 테스트 기록, 후속 계약을 추출하라. HANDOFF는 검증 대상이지 근거가 아니다.
4. 적용되는 `AGENTS.md`의 작업 규칙.

# 검사 절차

1. **항목 분해:** 가이드의 기능, 동작, UI, 데이터, 인터페이스, 제한, 예외 처리와 완료 조건을 독립적으로 판정할 수 있는 항목으로 나누어라. 확정 요구·조건부 요구·제안·후속 범위를 구별하라.
2. **ID 부여:** 규격서의 `REQ-*`/`DES-*` ID가 있으면 그 ID를 쓰라. 없으면 `VAL-<영역><번호>-NNN` 형식을 쓰라(예: `VAL-FE03-001`, `VAL-BE01-001`). 한 항목을 나누어 판정하면 `-001a`, `-001b`처럼 접미사를 붙여라. 재검증 때에도 같은 요구에는 같은 ID를 유지하라.
3. **체크리스트:** [보고서 템플릿](assets/verify-template.md)에 `ID | 항목 | 요구 내용 | 기준 | 검사 대상`을 먼저 채우고, 요구 내용의 출처 위치(문서·절)를 기록하라.
4. **HANDOFF 대조:** 구현·보류 주장을 실제 코드와 대조하라. 주장한 파일이나 기능이 없거나 가이드와 다르면 기록하라. merge-base 이후의 `git diff --stat`으로 HANDOFF에 없는 변경 파일도 확인하라. 요구하지 않은 추가 구현은 별도 발견 사항으로 기록하라.
5. **실행 검사:** 아래 [실행 명령](#실행-명령)을 실행하라. 명령, 리비전, 결과, 실패 요약을 남겨라. 과거 HANDOFF의 통과 기록은 현재 코드의 통과 증거가 아니다.
6. **항목별 판정:** 실제 결과, 파일 경로와 가능하면 줄 번호, 테스트 근거, 판정 이유를 기록하라. 사용자 결정으로 보류했다면 결정의 출처와 현재 적용 범위를 확인하라. 원래 완료 조건이 남아 있으면 완료 처리하지 말라.
7. **추적성:** 요구사항 → 설계 → 가이드 → 구현 → 테스트 연결을 확인하고, 끊긴 연결을 별도로 기록하라. 현재 워크플로우 밖의 후속 기능은 범위 밖이라고 밝혀라.
8. **작성:** 전체 건수, FAIL/WARNING/N/A 항목, 후속 조치, 미실행 범위를 요약하라. [보고서 작성](#보고서-작성) 규칙에 따라 저장하라.

# 실행 명령

저장소 루트의 `package.json`, `backend/pyproject.toml`, `.github/workflows/ci.yml`과 명령이 일치하는지 먼저 확인하라. 다르면 현재 설정 파일을 따르고 차이를 기록하라. 의존성이 없으면 `npm ci`, `uv sync --locked`로 설치할 수 있다.

**frontend (FE)** — 저장소 루트에서:

```bash
npm run lint
npm run typecheck
npm test
npm run build
npm run test:e2e
```

**backend (BE)** — `backend/`에서:

```bash
uv run ruff check src tests migrations
uv run ruff format --check src/backend/db tests migrations
uv run pytest -q
```

- 다른 영역의 코드도 변경되었다면(4단계 diff 기준) 그 영역의 명령도 실행하라.
- 실행할 수 없는 경우(Playwright 브라우저 없음, `TEST_DATABASE_URL`/PostgreSQL 없음 등) "미실행"으로 기록하고 환경 제약과 영향받는 항목 ID를 적어라. 실행하지 않은 명령을 통과로 적지 말라.
- 실패는 신규 회귀 / 기존 실패(`main`에서도 실패) / 환경 제약으로 구분하라.
- 문서만 변경된 워크플로우는 링크·ID·내용 정합성을 검사하고, 앱 테스트를 실행한 것처럼 보고하지 말라.

# 판정 기준

- **PASS**: 요구를 충족하는 실제 구현과 구체적인 확인 근거가 있다. 테스트가 필수 완료 조건이면 실행 결과도 확인하라.
- **FAIL**: 범위 안의 필수 구현이 없거나, 기준과 명확히 다르거나, 필수 테스트가 실패했다. HANDOFF의 보류 주장만으로 제외하지 말라.
- **WARNING**: 핵심 구현은 있으나 일부 차이, 잠재 결함, 증거·검증 부족이 있거나 승인된 보류로 원래 완료 조건이 남았다. 위험을 구체적으로 적어라.
- **N/A**: 조건이 발생하지 않았거나 명시적으로 현재 워크플로우의 범위 밖이다. 적용하지 않는 근거를 적어라. 자료가 부족하면 결과에 '판정 보류(증거 부족)'를 쓰고 WARNING으로 분류하라.

**mock·샘플 어댑터:** 가이드가 요구한 범위가 어댑터·샘플·mock까지라면, 그 범위를 충족할 때 PASS로 판정하라. 이 경우 결과에 `주석: 실연동 미확인(mock/샘플 기준)`을 반드시 적어라. 가이드가 실제 외부 연동까지 요구한다면 mock 통과는 연동의 증거가 아니다. 기준에 따라 FAIL이나 WARNING으로 판정하라.

완료와 미완료가 섞인 항목은 나누어 판정하라. 범위 안의 필수 항목에 FAIL과 미충족 완료 조건이 없을 때만 전체 완료를 선언하라. 전체를 판단할 자료가 부족하면 '판정 보류'로 기록하라.

# 보고서 작성

- 위치: 기준 가이드와 같은 폴더의 `<가이드 파일명>-VERIFY.md`. 예: `docs/workflow/frontend/03-OBJECTS-IMAGES-VERIFY.md`.
- **파일이 없으면** 템플릿 전체로 새로 작성하라.
- **파일이 이미 있으면** 기존 내용을 지우거나 고치지 말라. 파일 끝에 템플릿의 `## 검사 이력 N회차` 섹션을 새로 추가하라. N은 기존 회차 + 1이다. 문서 상단의 `최신 판정` 줄만 이번 회차 결과로 갱신하라.
- 쓰기가 불가능하면 쓸 수 있는 곳에 작성하고, 의도한 위치를 밝혀라.

# 보고 규칙

- 빈 셀은 `-`로 채우되, 필수인 판정 이유와 근거는 `-`로 대신하지 말라.
- 테스트 파일이 존재한다는 사실이나 HANDOFF의 주장만으로 PASS하지 말라.
- 문서에 없는 요구를 만들어내지 말라. 문서 충돌과 근거 없는 보류는 별도로 기록하라.
- 코드를 고치지 말고, 발견한 오류와 재현 방법을 보고하라.
- 템플릿의 예시 행은 보고서에 남기지 말라.

# 예외 처리

| 상황 | 처리 |
|---|---|
| 커밋되지 않은 변경 | 검사 중지, 파일 목록 보고, VERIFY 미작성 |
| 기준 가이드 없음 | 검사 중지, 누락 보고 |
| HANDOFF 후보가 0개 또는 여러 개 | 검사 중지, 후보 목록 보고 |
| 명령 실행 불가 | 미실행 + 사유 + 영향 ID 기록, 나머지 검사 계속 |
| 문서 간 충돌 | 임의로 해석하지 말고 "추가 구현·문서 충돌"에 기록 |

# 완료 조건

- 가이드의 모든 범위 내 항목에 ID·근거·판정이 있다.
- 실행 명령마다 결과 또는 미실행 사유가 있다.
- HANDOFF의 모든 구현·보류 주장이 대조되어 있다.
- `-VERIFY.md`가 작성되었거나(신규), 새 회차 섹션이 추가되었다(재검증).
